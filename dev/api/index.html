API

Everything that OhMyThreads.jl exports (tforeach, tmapreduce, treduce, tmap, tmap!, tcollect, @tasks, @set, @local, @task_index, @allow_boxed_captures, chunks, index_chunks, the other schedulers, ...) is re-exported; see the OhMyThreads.jl documentation.

Schedulers

ThreadTeams.TeamScheduler — Type
TeamScheduler()

OhMyThreads.jl scheduler (also scheduler = :team) that runs a parallel operation on the worker pool: the input is split into one contiguous chunk per thread of the :default thread pool, chunk 1 runs on the calling task and chunk c on worker c. The calling task also runs every chunk whose worker has not picked it up in time (a sleeping worker, or a thread that the OS does not schedule), so a loop never waits for an idle worker. Lowest overhead; best for loops with balanced iterations.

Only one parallel operation runs on the pool at a time. One started while another task is using the pool runs on Threads.@spawned tasks instead, and one started from inside a chunk (nested) runs serially. Chunks run in the dynamic scope (ScopedValues, logger) and world age of the caller. If chunks throw, the exception of the first failing chunk is rethrown after all started chunks have finished.

The task index (OhMyThreads.WithTaskIndex, @task_index) is the chunk index. For chunks/index_chunks inputs it is the position of the chunk, as with the other schedulers. Task-local values (@local) live in the worker tasks, which persist: they are initialized once per worker and reused across loops.

The scheduler takes no keyword arguments. In particular ntasks is not supported: chunks are not guaranteed to run at the same time, so @barrier can not be used.

ThreadTeams.GreedyTeamScheduler — Type
GreedyTeamScheduler(; nchunks = 0, chunksize = 0)

OhMyThreads.jl scheduler (also scheduler = :greedyteam) that runs a parallel operation on the worker pool with load balancing: the input is split into nchunks contiguous chunks (default 4 * nworkers()), or into chunks of chunksize elements, and the calling task and the workers take chunks from a shared counter until none are left. Use it for loops whose iterations take very different amounts of time. See TeamScheduler for the semantics shared by both schedulers.

Chunks are contiguous, and reductions combine the chunk results in chunk order, so the reducing operator only has to be associative (not commutative), and the result is deterministic for a given number of chunks. The task index is the chunk index.

The team

ThreadTeams — Module
ThreadTeams

A pool of persistent ("parked") worker tasks that runs OhMyThreads.jl's parallel functions (tforeach, tmapreduce, tmap, @tasks, ...) with low per-loop overhead. The package re-exports the OhMyThreads.jl API and adds two schedulers:

  • TeamScheduler (scheduler = :team): one contiguous chunk per thread of the :default thread pool, chunk 1 on the calling task, the others on the workers;
  • GreedyTeamScheduler (scheduler = :greedyteam): more chunks than threads, taken by the caller and the workers as they become free (load balancing).

There is one sticky worker task per thread of the :default thread pool. After a loop, idle workers spin for a short while (see ThreadTeams.set_spin_time!) before they go to sleep, so that back-to-back loops do not pay for task creation, scheduling and wake-up.

Pool controls: ThreadTeams.nworkers, ThreadTeams.set_spin_time!, ThreadTeams.spin_time, ThreadTeams.parallel_phase, ThreadTeams.shutdown!.

With Enzyme.jl loaded, parallel operations on the team can be differentiated in forward and reverse mode (a package extension; see the README).

ThreadTeams.nchunks — Function
ThreadTeams.nchunks(itr, scheduler = TeamScheduler()) -> Int

Number of chunks a parallel operation over itr would be split into right now: with the TeamScheduler at most one per thread of the :default thread pool, with the GreedyTeamScheduler as many as it asks for, and at most one per element. 1 means that the operation runs serially, which is the case with a single thread and inside another parallel operation on the pool. (During precompilation, loops also run serially, but that is decided later.)

ThreadTeams.set_spin_time! — Function
ThreadTeams.set_spin_time!(seconds::Real)

Set how long an idle worker busy-waits for the next parallel loop before it goes to sleep. The default is 100e-6 (100 µs). The time counts from the end of the parallel loop: a worker that finished its chunk early keeps spinning while the loop waits for the other chunks. Takes effect the next time a worker starts waiting.

Longer spinning makes parallel loops that follow each other with short serial gaps cheaper (waking up a sleeping worker costs about 10 µs), but idle workers keep their CPU busy for that long after every loop. 0 makes workers go to sleep right away (lowest CPU use, highest latency). To keep the workers spinning only during a part of the program, use ThreadTeams.parallel_phase.

On CPUs with performance and efficiency cores (recent Intel CPUs, Apple silicon), spinning cores take power and turbo headroom from the busy ones. LLVM's and GCC's OpenMP runtimes do not spin by default on such CPUs; consider set_spin_time!(0) there.

ThreadTeams.parallel_phase — Function
ThreadTeams.parallel_phase(f)

Call f() and return its result. While f runs, idle workers keep spinning instead of going to sleep after spin_time(), and sleeping workers are woken up at the start. Use it around a part of the program with many parallel loops separated by serial work that takes longer than the spin time, so that the loops do not pay for waking up the workers (about 10 µs each). Idle workers still go to sleep when their thread has another task to run, but otherwise keep their CPU busy until f returns.

Phases may be nested and may be active in several tasks at once.

ThreadTeams.parallel_phase() do
    for step in 1:nsteps
        serial_part!(state)       # e.g. 1 ms
        tforeach(eachindex(u); scheduler = TeamScheduler()) do i
            ...
        end
    end
end

ThreadTeams.shutdown! — Function
ThreadTeams.shutdown!()

Stop all worker tasks and drop the pool. Waits for a parallel region running in another task to finish first. The next parallel loop starts a new pool.

Throws an error when called from inside a parallel loop.
