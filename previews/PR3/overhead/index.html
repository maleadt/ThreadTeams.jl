Overhead

Per-loop time for a loop with 64 trivial iterations (x[i] += 1.0), benchmark/overhead.jl, pinned to 8 cores (taskset -c 8-15) of a Ryzen 9 5950X, Julia 1.12.7 and 1.13.1, OPENBLAS_NUM_THREADS=1. Polyester.jl 0.7.18 was loaded from a separate environment for comparison (* on 1.13 from an earlier run, with 0.7.19); OhMyThreads.jl 0.8.7 and KernelAbstractions.jl 0.10.0 (foreach_index on the CPU backend, followed by synchronize) come from the benchmark environment. Values are min / median in µs.

These numbers come from one shared machine, with other jobs running on the same cores. Minima are more reliable than medians.

  • Pass the scheduler as an object. A symbol (scheduler = :team, @set scheduler = :team) is resolved by OhMyThreads with a dynamic dispatch, which costs about 0.3 µs and 64 bytes per loop.
  • GreedyTeamScheduler() splits the 64 iterations into 32 chunks (4 per thread) that are handed out one by one, hence the higher cost; with chunksize or nchunks set to match the loop, it costs about as much as the static schedule.
  • -t 8 is the default since Julia 1.12: 8 default threads plus one interactive thread, so 9 threads share 8 cores. Threads.@threads :static then pays about the scheduler's sleep threshold (100 µs) per loop. Its sticky tasks must wait until the OS deschedules a thread that is spinning in the scheduler. :dynamic is not affected, and neither are the team and Polyester. The worker tasks already run, and the caller (on the interactive thread) runs chunk 1 while one default thread stays unused.
  • OhMyThreads' :static scheduler also uses sticky tasks and has the same problem with -t 8.
  • KernelAbstractions 0.10 runs CPU kernels through POCL (CPU() is a POCLBackend()), so foreach_index compiles the body as a kernel. A launch costs about as much as a @threads loop, but it allocates much less.
  • With -t 8,0 (no interactive thread) @threads :static costs about 2–3 µs.
  • Waking up workers that have gone to sleep costs about 10–15 µs, for the team and for @threads alike. Raise the spin time when loops are separated by longer serial phases.

Where the time goes

Hardware counters per loop on the calling thread (benchmark/counters.jl, LinuxPerf.jl, same loop and machine as above, Julia 1.12, -t 8):

(Ranges over four runs; the spread comes from other jobs on the machine.)

The cache misses are the hand-off: every worker's command field is a cache line that moves between the calling thread's core and the worker's core. A perf profile of the calling thread puts more than half of its time into that hand-off (storing the commands, checking afterwards which chunks the workers have not taken, and waiting for the last worker). The two IdDict lookups (chunk function slot, partials buffer) cost about 1%; OhMyThreads' entry (tmapreduce keyword handling, the scheduler object) and mapreduce over the first chunk account for the remaining instructions, which is where the team executes about three times as many instructions as Polyester at a similar cycle count.

Two details keep the hand-off cheap: the command stores are release stores followed by one fence rather than sequentially consistent stores (an xchg per store would wait for each cache line in turn, where plain stores overlap in the store buffer), and the check for untaken chunks loads before it compare-and-swaps (a failed compare-and-swap would still take the line away from the worker, which then has to take it back). Together they removed about a quarter of the calling thread's cycles.
